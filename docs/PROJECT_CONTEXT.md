## 0. Как использовать этот файл

**Человеку.** Дай этот файл своему ИИ-агенту (Claude Code, Codex) и скажи: «Прочитай docs/PROJECT_CONTEXT.md. Моя роль — N». Подробное задание тимлида лежит в `docs/lead-spec.md`.

**ИИ-агенту.**
1. Прочитай файл целиком.
2. Если человек не назвал роль (1, 2, 3 или 4), спроси.
3. Работай только в папках своей роли (раздел 5). Чужие папки не трогай.
4. Контракты (раздел 4) — черновик, пока в репозитории нет папки `shared/`. После этапа S0 источником правды являются файлы в `shared/`.
5. Контракты не меняй сам. Если нужно изменение, остановись и опиши предложение в `docs/CONTRACT_CHANGES.md`, затем сообщи человеку (раздел 12).
6. Перед работой прочитай `AGENTS.md` в корне репозитория: там короткие обязательные правила.
7. Язык общения с человеком: русский. Код и идентификаторы: английский.

## 1. Задание хакатона

### 1.1. Исходное условие

Необходимо реализовать виртуальную реальность с помощью three.js в браузере. Должен быть многопользовательский режим, ноутбуки соединены через LAN/Wi-Fi. Данные об объектах подгружаются с сервера в зависимости от положения игрока, на клиенте кешируются не более 10% общих данных всего мира. Клиенты получают от сервера передвижения других игроков. Двунаправленный обмен: WebSocket или аналоги, они должны работать после авторизации. Состояние игроков сохраняется в БД или файле на сервере.

Игроки могут взаимодействовать друг с другом, а также с ИИ-агентами. Агенты обладают индивидуальностью (например, с Эйнштейном можно поговорить про теорию относительности, а с Геродотом про путешествие в Египет). Это не заранее написанные скрипты: агенты адаптируются к предыдущим действиям игрока, рассказывают по-другому, пропускают то, что уже говорили.

ИИ-вычисления проводятся только локально, во время игры компьютеры отключены от интернета. Допустимы локальные LLM с файлами поведения, конечные автоматы, поиск информации в тексте, коллаборативная фильтрация и т. д.

Игра должна иметь социальный смысл: общение с иностранцами, изучение стран, истории, математики или других знаний. Нужно сделать красиво, удобно, полезно и производительно.

Можно использовать Babylon.js и three.js как дополнение, но в основе должно лежать одно из двух. Фронтенд на JavaScript, бэкенд на любом языке.

### 1.2. Уточнения организаторов

- Только один компьютер является сервером: на нём бэкенд, БД, ИИ и всё остальное для бэка. Остальные ноутбуки — клиенты, на них только браузер.
- Игру можно запускать на компьютере с сервером, тогда Wi-Fi выключен. Либо подключаться с другого ноутбука-клиента.
- Модели ИИ любые: конечные автоматы, линейные регрессии для классификации, коллаборативная фильтрация, нейросети, небольшая LLM (например, 3 млрд параметров).
- ИИ запускается на сервере. Для оптимизации можно запускать нейросети на JS в браузере клиента, но кроме браузера на клиентах ничего быть не должно.
- В демонстрации вечером нужно подготовить оба варианта: сначала по Wi-Fi все соединены и показаны на нескольких ноутбуках, потом Wi-Fi отключён и на ноутбуке сервера всё работает автономно.

## 2. Идея проекта

**«Город профессий»** — 3D-город для профориентации. Каждый район посвящён направлению профессий (медицина, инженерия, IT, образование, транспорт, сервис). Игрок разговаривает с ИИ-наставниками, решает мини-задачи профессии и объединяется с другими игроками для кооперативных заказов. В конце ему предлагаются профессии, которые ему подходят.

Социальный смысл: школьники и студенты редко знают, чем на самом деле занят врач, инженер или диспетчер. Здесь они пробуют работу на практике и видят, что почти любая профессия командная.

### 2.1. Игровой цикл (полная версия)

1. Регистрация и вход.
2. Стартовая анкета (3–5 вопросов) формирует начальный вектор интересов.
3. Прогулка по городу: районы подгружаются по мере приближения.
4. Разговор с наставником о профессии.
5. Соло-задача района.
6. Кооперативный заказ, требующий нескольких профессий.
7. Портфолио результатов.
8. Рекомендации профессий.

### 2.2. Районы (полная версия, шесть)

| Район | Агенты | Соло-задача | Кооперативный заказ |
|---|---|---|---|
| Медицина | Терапевт, лаборант | Опросить пациента и выбрать анализы | «Срочный пациент» |
| Инженерия и строительство | Инженер-конструктор, архитектор | Собрать мост, чтобы он выдержал нагрузку | Архитектор, инженер, строитель |
| IT | Разработчик, тестировщик | Найти ошибку в «сломанной» схеме | Разработчик и тестировщик |
| Образование и наука | Учитель, исследователь | Объяснить тему агенту-«ученику» | Подготовить урок |
| Транспорт и авиация | Диспетчер, пилот | Построить маршрут | Диспетчер ведёт борт на посадку |
| Сервис и кулинария | Шеф-повар, администратор | Приготовить блюдо по тайминг-задаче | Ресторан в час пик |

### 2.3. Объём черновика (первые 5–6 часов)

**Входит:**
1. Регистрация и вход, WebSocket только после авторизации.
2. Мир из 144 чанков (12×12) со счётчиком кеша на экране.
3. Два игрока видят друг друга и плавно двигаются.
4. Один район «Больница» с агентом-терапевтом: диалог со стримингом, память о сказанном, поиск по 25–30 карточкам знаний.
5. Одна соло-задача «Пациент»: игрок выбирает вопросы, получает данные, ставит диагноз, проверяет код.
6. Сохранение позиции, диалоговой памяти и результата задачи в SQLite.
7. Запуск командой `npm start` и подключение второго ноутбука по сети.
8. Боты для режима без Wi-Fi.

**Откладывается:** остальные районы, кооперативные заказы, анкета, рекомендации, портфолио, эмбеддинги (в черновике хватит BM25), WebXR, адаптивное разрешение, QR-код (по возможности), автопереподключение (по возможности).

**Нельзя резать:** авторизация перед WebSocket, счётчик кеша, память агента.

## 4. Архитектура и контракты

```
Браузеры игроков  <-- HTTP + WebSocket (MessagePack) -->  Сервер Node.js
(three.js, Preact)                                         ├─ HTTP и авторизация
                                                           ├─ WebSocket-шлюз
                                                           ├─ Мир и чанки (зеркало кеша)
                                                           ├─ Мозг агентов ──> Ollama (LLM, bge-m3)
                                                           ├─ Задачи (конечные автоматы)
                                                           └─ SQLite, файлы чанков и контента
```

### 4.1. Константы мира (`shared/constants.js`)

| Константа | Значение |
|---|---|
| `CHUNK_SIZE` | 64 (метры) |
| `WORLD_CHUNKS_X`, `WORLD_CHUNKS_Z` | 12, 12 |
| `WORLD_CHUNKS_TOTAL` | 144 |
| `VIEW_RADIUS` | 1 (область 3×3 = 9 чанков) |
| `CACHE_FRACTION` | 0.1 |
| `CACHE_MAX_CHUNKS` | 14 (то есть $\lfloor 0{,}1 \cdot 144 \rfloor$) |
| `TICK_HZ` | 15 |
| `MAX_SPEED` | 9 м/с (проверка с допуском ×1.5) |
| `TALK_DISTANCE` | 8 м |
| `SPAWN` | центр чанка (6, 6), район больницы |

Система координат: правая, ось Y вверх, метры, поворот `ry` в радианах. Чанк `(cx, cz)` покрывает `x ∈ [cx·64, (cx+1)·64)` и `z ∈ [cz·64, (cz+1)·64)`.

### 4.2. Правило кеша 10%

Сервер сам ведёт зеркало кеша каждого клиента и командует, что загрузить и выгрузить. Клиент ничего не решает сам.

1. Обязательное множество $R$: чанки с $\max(|\Delta cx|, |\Delta cz|) \le 1$ вокруг игрока (в пределах мира), до 9 штук.
2. Резерв: ещё $14 - |R|$ ближайших чанков по расстоянию до центра чанка.
3. Желаемое множество $D = R \cup \text{резерв}$, $|D| \le 14$.
4. Порядок: сначала `chunk_unload` для `mirror \ D`, затем `chunk_load` для `D \ mirror`, затем `cache_stats`.
5. Дополнительно сумма байтов чанков у клиента не больше $0{,}1 \cdot B_{\text{мир}}$.
6. Клиенты не используют HTTP-кеш, IndexedDB и Service Worker для данных мира. Чанки идут по WebSocket.

HUD показывает: «Чанки: X из 144 (Y%), лимит 14». Пример: при 9 загруженных чанках $9/144 = 6{,}25\%$.

### 4.3. Протокол WebSocket (`shared/protocol.js`)

Кодирование: MessagePack, бинарные кадры. Каждое сообщение — объект с полем `t` (тип). Версия протокола `proto: 1`. Подключение: `GET /ws?ticket=<ticket>`; тикет одноразовый, живёт 30 секунд, выдаётся `POST /api/ws-ticket`. Без верного тикета сервер отвечает 401 до апгрейда.

**Клиент → сервер**

| `t` | Поля | Примечание |
|---|---|---|
| `hello` | `ticket, proto` | Первое сообщение |
| `pos` | `x, y, z, ry, anim, seq` | 15 раз в секунду. `anim`: 0 стоит, 1 идёт, 2 бежит |
| `chat` | `text` | До 200 символов |
| `npc_talk` | `agentId, text, reqId` | Реплика агенту |
| `task_answer` | `taskId, payload` | Ответ на задачу |

**Сервер → клиент**

| `t` | Поля | Примечание |
|---|---|---|
| `welcome` | `proto, playerId, name, state, consts` | `state`: позиция, прогресс |
| `player_join` | `id, name, appearance` | Игрок вошёл в зону интереса |
| `player_leave` | `id` | Вышел |
| `players` | `tick, list: [[id,x,y,z,ry,anim], ...]` | 15 Гц, только соседи (зона 3×3 чанков) |
| `correct` | `x, y, z` | Принудительная коррекция позиции |
| `chat` | `from, text, ts` | Соседям по чанкам |
| `chunk_load` | `cx, cz, data` | `data` — байты чанка |
| `chunk_unload` | `cx, cz` | Всегда раньше `chunk_load` в пакете |
| `cache_stats` | `loaded, max, worldTotal, bytes, bytesMax` | После изменения |
| `agent_queue` | `agentId, reqId, position` | Место в очереди |
| `agent_token` | `agentId, reqId, token` | Поток ответа |
| `agent_done` | `agentId, reqId` | Конец ответа |
| `agent_error` | `agentId, reqId, message` | Ошибка |
| `task_state` | `taskId, state` | Состояние задачи |
| `error` | `code, message` | `bad_msg`, `too_far`, `rate_limit`, `unauth` |

Лимиты: `pos` до 30 в секунду, `chat` до 5 в секунду, `npc_talk` до 1 в секунду на пользователя; `task_answer` — до 20 в секунду (серия попаданий по окнам).

**`task_answer` / `task_state` (станция «Пожарный», `taskId: 'firefighter_station_v1'`).** Клиент отправляет только намерение: `payload: {action}`, где `action` — `start`, `accept_briefing`, `equip`, `window_hit`, `pickup_mannequin`, `deliver_mannequin`, `report` или `resume` (только прочитать состояние). Для `window_hit` читается ещё `index` — номер окна учебной стены, целое 0..3 (сервер проверяет его и сверяет направление взгляда с этим окном). Остальные поля payload сервер не читает: владелец прогресса — `userId` соединения, позиция и взгляд (`ry` из принятого `pos`) — серверные, `state`/`done`/`progress` из клиента не принимаются. Ответ `task_state.state` — `{stage, equipped, windows, carryingMannequin, mannequinDelivered, done, feedback, changed}`, где `windows` — массив из 4 целых 0..12 (число попаданий по каждому окну, 12 — потушено); записи прежнего формата с `fireHits` сервер при чтении переводит в `windows`; `changed: true` только если переход записан в SQLite. При сбое базы приходит `{error: 'storage', feedback}` (при сбое записи — с прежним состоянием), прогресс не меняется. `task_state` присылается и сразу после `welcome` (восстановление после входа и переподключения). Мировые координаты точек станции и преобразование из локальных координат preview — `client/stations/firefighter/layout.js`.

**`task_answer` / `task_state` (Radio, `taskId: 'radio_station_v1'`).** Действия: `open`, `select_category` (`weather|science`), `generate_script`, `start_broadcast`, `complete_broadcast`, `new_broadcast`. Сценарий готовится асинхронно; сетевой слой ожидает task handler, а клиент получает один итоговый `task_state` без потоковых токенов и без нового типа сообщения. Временный этап генерации не сохраняется; устойчивые этапы: `idle`, `choose_topic`, `ready`, `on_air`, `completed`. `task_progress` хранит категорию, сценарий, последние 5 завершённых `recentTopicIds`/заголовков и `completedBroadcasts`. `complete_broadcast` идемпотентен. При отключении соединения `AbortSignal` останавливает генерацию и поздний `task_state` не отправляется. Science берёт только локальный факт из `content/radio/science-facts.js`; модель может только адаптировать его для чтения вслух. При ошибке Ollama используется исходный факт или локальный вымышленный weather script.

### 4.4. HTTP API

| Метод и путь | Назначение |
|---|---|
| `POST /api/join` `{name, room}` | Вход по имени и коду комнаты (четыре латинские буквы, новый при каждом запуске сервера и показан в терминале), ответ `{token, user}`. Ошибки: `bad_name`, `bad_room` (400/403), `name_taken` (409, имя занято играющим), `too_many` (429, после 10 неверных кодов за минуту с одного адреса) |
| `GET /api/local-room` | Код комнаты `{room}` для экрана владельца сервера. Только если TCP-соединение пришло с loopback или с собственного LAN-адреса этого компьютера и `Host` — `localhost`/IP-адрес (плюс проверки `Origin` и `Sec-Fetch-Site`); `X-Forwarded-For` не учитывается. Остальным — 404. Это удобство, не авторизация: `/api/join` всегда проверяет код |
| `POST /api/register`, `POST /api/login` `{name, password}` | Только при `passwordAuth: true` в конфиге сервера (по умолчанию выключено, иначе обходят код комнаты) |
| `POST /api/ws-ticket` (заголовок `Authorization: Bearer <token>`) | Одноразовый тикет WebSocket |
| `GET /api/me` | Данные пользователя |
| `GET /health` | `{ok: true, ...}` |
| `GET /admin`, `/admin/stats` | Только с `127.0.0.1` |

Токен клиент хранит в `sessionStorage`. Адреса относительные, WebSocket через `location.host`.

### 4.5. Формат чанка (черновик, финал согласуют роли 1 и 2)

Файл `generated/chunks/{cx}_{cz}.bin` — один объект MessagePack:

```
{ v: 1, cx, cz, zone: 'hospital' | 'park' | 'plain',
  heights: Float32Array(17*17),            // 16×16 ячеек по 4 м
  instances: [[prefabId, x, y, z, ry, scale], ...],
  npcs: [{ id, agentId, x, y, z, ry }] }
```

Индекс `generated/world.json`: `{ v:1, chunkSize, chunksX, chunksZ, totalBytes, bytes: {"cx_cz": n}, prefabs: [{id, name, model, collider}], districts: [{id, name, chunks}], npcs: [...] }`. Папка `generated/` в git не коммитится. Пока `tools/build-world` (роль 1) не готов, роль 2 выдаёт простые фикстуры (`npm run world:fixtures`).

### 4.6. База данных (`server/db/schema.sql`, кратко)

## 7. Роль 1. Клиент и 3D

**Зона:** всё, что видно на экране, сеть клиента и производительность.

**Требования:**
1. Vite и three.js, `WebGLRenderer`, `pixelRatio = min(devicePixelRatio, 1.5)`, потолок 60 FPS.
2. Управление: захват мыши (pointer lock), `WASD`, `Shift` — бег. `E` — говорить с ближайшим NPC, `Enter` — чат, `Esc` — закрыть панель. При открытии панели интерфейса мышь освобождается через `api.ui.unlockPointer()`.
3. Коллизии: капсула против карты высот и AABB инстансов (поле `collider` в библиотеке префабов). Без физического движка.
4. Чанки: разбор объекта MessagePack, меш рельефа из `heights` (17×17), инстансы одного префаба группируются в `InstancedMesh` (по чанку). При `chunk_unload` убираем и вызываем `dispose()` для геометрий и материалов чанка. Общие модели и текстуры не удаляем (счётчик ссылок).
5. Сеть клиента: регистрация и вход, тикет, WebSocket по `location.host`, токен в `sessionStorage`. Позиции отправляются 15 раз в секунду.
6. Другие игроки: буфер снимков, отображение с задержкой около 100 мс и интерполяцией. Имя над головой (`CSS2DRenderer`). Аватар: простая low-poly фигура.
7. HUD: FPS, пинг, «Чанки: X из 144 (Y%), лимит 14». Значения берутся из `cache_stats`.
8. `tools/build-world`: по `content/map.json` (роль 4) и библиотеке префабов генерирует 144 чанка в `generated/chunks/` и индекс `generated/world.json`. Реальный контент только у района больницы, остальные чанки — «плоская земля и редкие деревья».
9. Производительность: ориентир до 200 draw calls, до 150 тысяч видимых треугольников, тень от одного источника света или без теней.
10. `api` для интерфейса (раздел 4.9) и событие `npc_near`.
11. Ресурсы: модели CC0 хранятся в `assets/` с файлом лицензий, общий размер десятки мегабайт. Никаких CDN и веб-шрифтов.

**Приёмка:**
- Ходьба без проваливаний, 60 FPS на M4 Pro.
- Второй игрок движется плавно.
- Счётчик чанков не превышает 14.
- Режим B: окно на `localhost` работает без Wi-Fi.

## 9. Роль 3. ИИ-агенты

**Зона:** `server/agents`, `server/rec`, `tools/agent-eval`.

### 9.1. Что должно получиться

Агент с индивидуальностью, который помнит, что уже рассказывал конкретному игроку, не повторяется и меняет подачу. Это не скрипт: ответ формулирует локальная LLM, а решения принимает код.

### 9.2. Конвейер ответа

1. Определить тему реплики: сходство с тегами карточек (на первом этапе правила и BM25, позже эмбеддинги `bge-m3`) без вызова LLM.
2. Загрузить память пары «игрок — агент» из SQLite: `told_cards`, `summary`, последние реплики.
3. Найти карточки знаний. Гибридный поиск: BM25 со стеммингом русского плюс (позже) косинус `bge-m3`. Штраф за уже сказанное:

$$\text{score}'_c = \text{score}_c - \lambda \cdot \mathbb{1}[c \in S_{u,a}]$$

где $S_{u,a}$ — множество карточек, которые агент $a$ уже рассказал игроку $u$, а $\lambda$ — вес штрафа.
4. Собрать промпт. Порядок важен для кеша префикса: сначала неизменная часть (персона, правила), затем переменная (профиль игрока, найденные карточки, сводка памяти, последние реплики). Цель: до 800 токенов.
5. Сгенерировать ответ через Ollama (`POST /api/chat`, `stream: true`, `think: false`, `keep_alive: -1`, `num_ctx: 4096`). Ориентир параметров для Qwen3 без рассуждений: `temperature` около 0,7, `top_p` около 0,8, `top_k` около 20 (проверить на месте). Ответ не длиннее 80–100 токенов.
6. После ответа: пометить использованные карточки как «сказано», обновить сводку и счётчики тем, обновить вектор интересов.
7. Если LLM не ответила за таймаут (около 20 секунд) или недоступна, ответить шаблоном по лучшей найденной карточке.

### 9.3. Параллельность и очередь

Два слота генерации (`OLLAMA_NUM_PARALLEL=2`), остальные запросы ждут в очереди, о месте в очереди сообщаем через `onQueue`. Модель прогревается при старте сервера.

### 9.4. Правила поведения агента

- Агент говорит от лица персонажа и не выходит из роли.
- Использует только факты из найденных карточек; если ответа нет, честно говорит, что не знает, и предлагает другую тему.
- Агент рассказывает о профессии и не даёт реальных медицинских советов (это образовательная игра).
- Не повторяет уже сказанное; ссылается на прошлый разговор («про учёбу мы уже говорили»).

### 9.5. Рекомендации (после черновика)

Вектор профессии $\mathbf{q}_j$ и вектор интересов игрока $\mathbf{p}_u$ (шесть осей: практическая, исследовательская, творческая, социальная, предпринимательская, организационная). Близость:

$$\mathrm{sim}(u, j) = \frac{\mathbf{p}_u \cdot \mathbf{q}_j}{\lVert \mathbf{p}_u \rVert \, \lVert \mathbf{q}_j \rVert}$$

Обновление интересов после разговора с агентом профессии $a$:

$$\mathbf{p}_u \leftarrow (1-\alpha)\,\mathbf{p}_u + \alpha\,\mathbf{q}_a$$

где $\alpha$ зависит от вовлечённости игрока. Коллаборативная фильтрация по соседям $N(u)$:

$$\hat{r}_{u,j} = \frac{\sum_{v \in N(u)} \mathrm{sim}(u, v)\, r_{v,j}}{\sum_{v \in N(u)} \lvert \mathrm{sim}(u, v) \rvert}$$

Игроков мало, поэтому основа — близость векторов, а коллаборативная часть работает поверх заранее заложенных виртуальных профилей.

Дополнительно (по желанию): классификатор намерения реплики (мультиномиальная логистическая регрессия на TF-IDF) для маршрутизации без LLM:

$$P(y=k \mid \mathbf{x}) = \frac{e^{\mathbf{w}_k \cdot \mathbf{x} + b_k}}{\sum_{j} e^{\mathbf{w}_j \cdot \mathbf{x} + b_j}}$$

### 9.6. Инструменты и приёмка

- CLI `npm run agent-chat -- --agent therapist` для проверки без сервера и клиента.
- `tools/agent-eval`: набор из 10–20 тестовых диалогов и сравнение `qwen3:4b` и `qwen3:8b`.

## 11. План демонстрации вечером

**Часть 1. Режим A (Wi-Fi).**
1. Сервер запущен, три-четыре ноутбука подключаются по `http://<IP>:3000`.
2. Показываем: вход, мир, другие игроки, счётчик кеша, диалог с агентом, память агента (возврат к разговору), задача.

**Часть 2. Режим B (автономный).**
1. Выключаем Wi-Fi на серверном ноутбуке.
2. Открываем `http://localhost:3000`, входим двумя окнами (второе в режиме инкогнито), запускаем ботов (`npm run bots`).
3. Показываем диалог с агентом без сети, игроков, ботов и сохранённый прогресс.

**Подготовка (пока есть интернет):** `npm ci`, `ollama pull qwen3:8b`, `ollama pull bge-m3`, `npm run build`, проверка `npm run check:offline`. Резервная копия: `git bundle create city.bundle --all` и копия папки проекта на флешку. Запасной план: короткое видео работы на случай сбоя.

Важно: игровой клиент хоста в режиме B должен быть открыт через `localhost`, а не через LAN-адрес, иначе при отключении Wi-Fi соединение оборвётся.

## 12. Правила для ИИ-агентов (кратко, полный текст в `AGENTS.md`)

- Проект офлайн: никаких внешних URL, CDN, веб-шрифтов, аналитики.
- JavaScript с ES-модулями, без TypeScript. Клиент: относительные адреса, WebSocket через `location.host`, токен в `sessionStorage`.
- Правь только папки своей роли. `shared/` меняет только роль 2.
- Контракт, зависимость вне списка, правка чужой папки, необратимое действие, двукратное падение теста: остановись и спроси человека.
- Не используй `git push --force`, `git reset --hard`, `git clean -fd`, `--no-verify`.
- Малые коммиты в формате `область: что сделано`; перед коммитом `npm run verify`.
- К каждой функции пиши автотест (встроенный `node:test`).
- Ты не видишь вживую игру: не утверждай, что результат «работает», пока не запустил проверку; для визуальных и сетевых проверок проси человека.

## 14. Происхождение цифр (для честности)

- Скорость генерации и размеры моделей — оценки по открытым замерам и экстраполяции; на M4 Pro 24 ГБ измерен только Llama 3.1 8B (около 34 токенов/с через Ollama). Перед демо замерить `qwen3:8b` на месте.
- Лимит памяти GPU на 24 ГБ — примерно 16–18 ГБ (от двух третей до 75% оперативной памяти по разным источникам).
- Мир 12×12 чанков выбран из условия $N_{\text{мир}} \ge \dfrac{N_{\text{видимых}}}{0{,}1}$: для области 3×3 нужно минимум 90 чанков.
