# ИИ-агент станции «Радиостанция»

> [!IMPORTANT]
> Этот документ является канонической спецификацией ИИ-агента станции Radio.
>
> Перед реализацией, интеграцией, изменением или ревью Radio AI этот файл необходимо прочитать полностью.
>
> Реализация Radio AI не должна противоречить требованиям этого документа без явного изменения спецификации.

## Назначение агента

ИИ-агент выступает редактором радиостанции. Он самостоятельно выбирает тип выпуска и конкретную тему, учитывает недавно прозвучавшие выпуски, готовит полный сценарий и передаёт его игроку до начала эфира.

Игрок не выбирает между `weather` и `science` и не назначает тему. Игрок читает подготовленный сценарий, выбирает скорость телесуфлёра, начинает эфир, читает текст, при необходимости ставит его на паузу или продолжает, а затем завершает выпуск.

## Основной цикл

```text
open
→ автоматический выбор категории и темы
→ generation
→ ready
→ игрок читает полный сценарий
→ игрок выбирает скорость
→ start
→ подтверждённое сервером состояние on_air
→ обратный отсчёт 3–2–1
→ ON AIR
→ телесуфлёр показывает группы по 2–3 слова
→ complete
→ new broadcast
→ агент автоматически запускает следующий цикл
```

Генерация завершается до эфира. Потоковые токены LLM не показываются на мониторе игрока. Нажатие «Новый выпуск» поручает агенту начать следующий выпуск; игрок не выбирает его тип или тему.

## Типы выпусков

### Weather

- Это учебный, полностью вымышленный прогноз.
- Он не сообщает реальную погоду и не использует реальные погодные данные.
- Для создания сценария не обращаются в интернет или к погодным API.
- Обязательный disclaimer добавляет сервер. Он должен оставаться в итоговом сценарии, в том числе при использовании fallback.
- Ориентир для сценария — 3–4 коротких предложения.
- Для темы используется идентификатор вымышленного сюжета; он не ссылается на реальную метеорологическую запись.

### Science

- Тема и исходный факт выбираются только из локального проверенного каталога.
- У каждой записи каталога есть стабильный `topicId`.
- Каталог, а не LLM, является источником научного содержания.
- LLM может переформулировать исходный факт, чтобы сделать выпуск понятным и удобным для чтения вслух.
- Запрещено добавлять новые факты, числа и причинно-следственные связи, которых нет в исходном факте.
- Запрещено расширять содержание знаниями модели или неподтверждёнными сведениями.
- Недавно использованные `topicId` исключаются из выбора, пока остаются другие доступные темы.

## Выбор категории и темы

В текущем MVP выбор категории контролируется серверной task logic:

1. Первый выпуск — `weather`.
2. Следующий — `science`.
3. Далее категории чередуются.

Конкретную тему для выбранного выпуска также выбирает агент/сервер. Игрок не управляет ни категорией, ни темой. Чередование можно позднее заменить другим контролируемым алгоритмом выбора, но решение остаётся на стороне агента/сервера.

Для Science выбор должен учитывать список недавних `topicId`. Если доступны другие факты, уже использованные идентификаторы не выбираются повторно. Список должен быть достаточно ограничен для хранения в прогрессе и сохранения разнообразия выпусков.

## Локальная AI-инфраструктура

Radio использует существующий AI subsystem проекта и локальную Ollama:

```text
Radio task
→ Radio AI service
→ существующий Ollama adapter
→ полный сценарий
→ состояние Radio task
→ клиент
```

Обязательные ограничения:

- Не использовать cloud AI API.
- Не отправлять запросы во внешние сети для генерации.
- Не создавать второй независимый Ollama client.
- Повторно использовать существующую AI-инфраструктуру проекта и её локальные ограничения.
- До передачи в состояние Radio task проверить структуру, категорию, тему и допустимость результата.

## Результат генерации

Логически готовый выпуск содержит:

```text
type       // weather или science
topicId    // стабильный идентификатор выбранной темы
title      // заголовок выпуска
script     // полный готовый текст
```

При передаче и хранении допустима другая форма полей, если эти четыре значения однозначно сохраняются и доступны клиенту. Для вымышленного Weather `topicId` описывает учебную тему. Для Science `topicId` обязан соответствовать записи локального каталога.

Поле категории в реализации может называться `category`; по смыслу оно соответствует `type`. Источник текста (`ollama` или локальный fallback) является служебными метаданными и не меняет смысл выпуска.

## Требования к сценарию

- Ориентир — 3–4 предложения и примерно 35–60 слов.
- Текущая цель генерации — около 45 слов.
- Язык простой, дружелюбный и подходящий аудитории детей.
- Текст предназначен для чтения вслух: короткие, понятные предложения и естественный ритм.
- Полный сценарий должен быть подготовлен до начала эфира и целиком показан игроку в состоянии Ready.
- Сценарий не должен передаваться игроку по токенам во время генерации.
- Для Weather в полный текст включается серверный disclaimer о вымышленном учебном прогнозе.
- Для Science текст ограничен содержанием выбранного проверенного факта.

Продуктовый ориентир — примерно 35–60 слов, а цель генерации — около 45 слов. Технический validator допускает 30–70 слов, чтобы устойчиво принимать небольшие вариации локальной LLM; этот более широкий допуск не меняет продуктовую цель.

## Состояния Radio

- `idle` — выпуск ещё не подготовлен; вход в Radio запускает автоматический выбор категории, темы и подготовку сценария.
- `generating` — временный runtime-процесс подготовки. Это не отдельное долговременное состояние продукта; после завершения он приводит к `ready`, а при ошибке использует fallback.
- `ready` — полный сценарий подготовлен и показан игроку; здесь же выбирается скорость телесуфлёра до эфира.
- `on_air` — сервер подтвердил начало выпуска; после этого клиент запускает обратный отсчёт и показывает текст в эфирном режиме.
- `completed` — выпуск завершён. Действие «Новый выпуск» автоматически запускает следующий цикл.

В task progress сохраняются данные, нужные для восстановления сценария и истории:

- категория/тип выпуска;
- `topicId`;
- заголовок и полный сценарий;
- `recentTopicIds`;
- `completedBroadcasts`.

Реализация может сохранять дополнительные безопасные поля, например заголовки недавно использованных тем или источник fallback. Скорость телесуфлёра — клиентская настройка; она не является серверным прогрессом Radio task.

## Ready state и скорость

После генерации игрок видит:

- категорию выпуска;
- заголовок;
- полный сценарий;
- выбор скорости телесуфлёра;
- кнопку «Начать эфир».

Скорость выбирается до эфира и не требует повторной генерации сценария:

| Режим | Интервал показа группы | Значение по умолчанию |
| --- | ---: | --- |
| Медленно | 1600 мс | |
| Обычно | 1000 мс | Да |
| Быстро | 650 мс | |

## Телесуфлёр

После обратного отсчёта сценарий делится на последовательные группы примерно по 2–3 слова. Одновременно на экране показывается одна группа. Текст крупный и расположен по центру; весь абзац не прокручивается по вертикали.

Пауза сохраняет текущую группу и позицию. Продолжение возобновляет показ с того же места. Последняя группа остаётся на экране до завершения эфира.

## Жизненный цикл ON AIR

Порядок включения физического индикатора и текста обязателен:

```text
сервер подтверждает состояние on_air
→ клиент показывает countdown 3–2–1
→ физический индикатор ON AIR включается
→ появляется первая группа телесуфлёра
```

Локальное нажатие игрока само по себе не включает физический ON AIR. Клиент ждёт подтверждённое состояние задачи от сервера. Пока идёт countdown, индикатор выключен и группа текста не показывается.

## Память и адаптация

Агент учитывает историю недавних выпусков. Для Science хранятся последние использованные `topicId`; агент избегает повторов, пока есть другие варианты. История обновляется после завершения выпуска, а не просто после генерации сценария.

Учет этой истории — механизм адаптации Radio agent к предыдущим действиям игрока: последующие выпуски учитывают, какие темы уже прозвучали. История помогает разнообразить контент, но не разрешает модели придумывать новые научные сведения.

## Fallback и доступность станции

Radio остаётся проходимой, если Ollama недоступна, отвечает ошибкой, превышает timeout или возвращает некорректный результат.

- **Science fallback** берёт готовый текст или исходное содержание из локального проверенного научного каталога и сохраняет соответствующий `topicId`.
- **Weather fallback** берёт заранее подготовленный учебный вымышленный прогноз и включает обязательный disclaimer.
- Fallback также учитывает историю тем и не должен без необходимости повторять недавний выпуск.
- Использование fallback не меняет выбранную категорию и не требует от игрока выбрать другой тип.

## Безопасность содержания

ИИ не является источником научного знания.

```text
local curated fact = source of truth
LLM = presentation layer
```

Для Science проверенный локальный факт задаёт предел содержания. Перефразирование допустимо только пока смысл остаётся в границах источника. Для Weather любая подача должна ясно обозначать вымышленный учебный характер и никогда не выдавать текст за настоящую погоду.

## Почему это ИИ-агент

Radio AI — это агентная система, потому что она самостоятельно:

- принимает решение о типе выпуска в рамках заданной политики;
- выбирает конкретную тему;
- создаёт новую формулировку сценария локальной LLM;
- учитывает историю выпусков и избегает повторов;
- передаёт результат в состояние задачи;
- использует локальный fallback при сбое модели.

Генеративность ограничена проверенными данными и правилами категории: в научном выпуске LLM меняет представление факта, но не становится его источником. В Weather агент создаёт только явно вымышленный учебный сценарий.

## Сверка текущей реализации

Сверка выполнена по состоянию рабочей копии на 2026-11-01. Этот раздел фиксирует наблюдаемые различия и не меняет утверждённую спецификацию.

- Сервер автоматически выбирает первую категорию как `weather`, затем чередует категории. Игроку `select_category` не даёт изменить выбор.
- Поле категории хранится как `category`; готовый объект также содержит `title`, `text`, `topicId` и служебный `source`. Это соответствует логической форме документа, где `text` — сценарий, а `category` — тип.
- Локальный генератор использует существующий `generateRadioScript` и общий Ollama adapter с loopback URL. Отдельный Radio Ollama client не создаётся; LLM не стримится клиенту.
- Science выбирается из локального каталога с `topicId`; история обновляется при завершении, а повторно использованные ID исключаются. Сейчас каталог содержит шесть фактов, история ограничена пятью последними ID.
- При ошибке генерации сервер выбирает локальный fallback. Для Weather сервер добавляет disclaimer; для Science используется текст на основе локального факта.
- Генератор нацелен примерно на 45 слов и 3–4 предложения. Validator tolerance составляет 30–70 слов для устойчивости к небольшим вариациям локальной LLM; продуктовый ориентир остаётся 35–60 слов.
- Выбор темы и generation являются runtime-процессом. Persisted stages — `idle`, `ready`, `on_air` и `completed`. Legacy progress со стадией `choose_topic` принимается для совместимости, нормализуется в `idle`, не показывается пользователю и автоматически продолжается при `open`. Таким образом, сохранённое состояние соответствует спецификации: `generating` не является persisted stage.
- В состоянии `ready` UI показывает категорию, заголовок, весь текст, скорость и кнопку начала. Скорость по умолчанию — `normal` (1000 мс); также реализованы 1600 и 650 мс.
- При подтверждённом или восстановленном состоянии `on_air` клиент проходит countdown 3–2–1, затем включает физический ON AIR и показывает телесуфлёр. Presentation phase logic защищает от повторного запуска countdown и таймеров. Первичное начало и восстановление эфира после reconnect теперь следуют одной последовательности, как требует спецификация.
- Телесуфлёр показывает 2–3 слова, хранит позицию и остаток задержки при паузе, продолжает с текущей группы и оставляет последнюю группу на экране.
- Скорость и позиция телесуфлёра не сохраняются в серверном task progress; это соответствует клиентскому характеру настройки скорости, но восстановление позиции эфира после полной перезагрузки не предусмотрено этим состоянием.
