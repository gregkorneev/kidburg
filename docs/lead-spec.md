# Спецификация для Claude Code: роль 2 «Сервер, сеть и интеграция» (тимлид)

Проект: «Город профессий» — многопользовательская 3D-игра для профориентации. Положи этот файл в репозиторий как `docs/lead-spec.md`.

## 0. Как пользоваться

1. Запускай Claude Code из корня репозитория.
2. Первый промпт: «Прочитай docs/lead-spec.md целиком. Составь план этапа S0, покажи его, затем выполняй.»
3. Этапы идут по порядку S0 → S1 → S2 → S3 → S4. После каждого этапа: приёмка (раздел «Приёмка»), `npm run verify`, коммит, тег, сообщение команде.
4. Если нужно изменить контракт или добавить зависимость вне списка, Claude Code не делает это сам: он пишет предложение в `docs/CONTRACT_CHANGES.md` и останавливается (см. раздел 11).

Время указано как T+ч:мин от начала работ. Цель всего проекта на этом этапе: черновик с одной профессией («Больница») за 5–6 часов.

## 1. Контекст и жёсткие ограничения

- Всё работает без интернета. Сервер, БД, ИИ запускаются на одном ноутбуке (MacBook Pro M4 Pro, 24 ГБ). Остальные ноутбуки — только браузер.
- Два режима демо. A: игроки подключаются по Wi-Fi к `http://<IP сервера>:3000`. B: Wi-Fi на сервере выключен, всё работает на нём одном через `http://localhost:3000` (два окна браузера как два игрока плюс боты).
- Фронтенд только на JavaScript (ES-модули, без TypeScript). Бэкенд на Node.js (JavaScript, ES-модули).
- Требования задания, которые касаются этой роли:
  - WebSocket работает только после авторизации.
  - Данные мира подгружаются по положению игрока. На клиенте одновременно не больше 10% данных мира.
  - Клиенты получают движения других игроков.
  - Состояние игроков сохраняется в БД на сервере.
- Хост сам играет, поэтому сервер не должен занимать лишние ресурсы: тик 15 Гц, никакой тяжёлой работы в главном цикле.

## 2. Общие правила работы Claude Code

1. Язык: JavaScript, ES-модули (`"type": "module"`). Node.js LTS (проверь `node -v`, нужна версия 22 или новее).
2. Никаких внешних адресов: ни CDN, ни шрифтов, ни аналитики. Все ресурсы локальные.
3. Адреса в клиенте относительные (`/api/...`, WebSocket по `location.host`), никаких жёстких IP и портов.
4. Токен авторизации хранится в `sessionStorage`, не в `localStorage` (чтобы два окна могли быть разными пользователями).
5. Не использовать `git push --force`, `git reset --hard`, `git clean -fd`, `--no-verify`.
6. Коммиты малые, формат сообщений: `область: что сделано` (`server: add ws ticket auth`, `shared: protocol v1`).
7. Перед каждым коммитом запускать `npm run verify`.
8. Менять только свои папки (таблица выше). Если нужна правка чужой папки, остановиться и сообщить.
9. Для каждой функции из этой спецификации писать автотест (встроенный `node:test`, без внешних тестовых фреймворков).
10. Логи на русском или английском, но единообразно; без ключей и секретов.
11. Не добавлять зависимости вне списка из раздела 12 без разрешения.

## 3. Константы мира (`shared/constants.js`)

| Константа | Значение | Смысл |
|---|---|---|
| `CHUNK_SIZE` | 64 | Размер чанка в метрах |
| `WORLD_CHUNKS_X`, `WORLD_CHUNKS_Z` | 12, 12 | Мир 12×12 чанков |
| `WORLD_CHUNKS_TOTAL` | 144 | $N_{\text{мир}} = 12 \cdot 12$ |
| `VIEW_RADIUS` | 1 | Обязательная область 3×3 (9 чанков) |
| `CACHE_FRACTION` | 0.1 | Доля мира у клиента |
| `CACHE_MAX_CHUNKS` | 14 | $\lfloor 0{,}1 \cdot 144 \rfloor = 14$ |
| `TICK_HZ` | 15 | Частота рассылки позиций |
| `MAX_SPEED` | 9 | Максимальная скорость игрока, м/с (с допуском ×1.5) |
| `TALK_DISTANCE` | 8 | Дальность разговора с NPC, м |
| `SPAWN` | центр чанка (6, 6) | Точка возрождения, район больницы |

Система координат: правая, ось Y вверх, единицы — метры, поворот `ry` в радианах. Чанк `(cx, cz)` покрывает `x ∈ [cx·64, (cx+1)·64)`, `z ∈ [cz·64, (cz+1)·64)`.

## 4. Протокол (`shared/protocol.js`)

Кодирование: MessagePack (`@msgpack/msgpack`), бинарные кадры WebSocket. Каждое сообщение — объект с полем `t` (тип). Модуль экспортирует константы типов, `encode(msg)`, `decode(buf)` и лёгкую валидацию (`validate(msg)` проверяет обязательные поля и типы). Версия протокола: `proto: 1`.

### Клиент → сервер

| `t` | Поля | Примечание |
|---|---|---|
| `hello` | `ticket`, `proto` | Первое сообщение после открытия сокета |
| `pos` | `x, y, z, ry, anim, seq` | 15 раз в секунду. `anim`: 0 стоит, 1 идёт, 2 бежит |
| `chat` | `text` | До 200 символов |
| `npc_talk` | `agentId, text, reqId` | Реплика игрока агенту |
| `task_answer` | `taskId, payload` | Ответ на задачу |

### Сервер → клиент

| `t` | Поля | Примечание |
|---|---|---|
| `welcome` | `proto, playerId, name, state, consts` | `state` содержит позицию и прогресс |
| `player_join` | `id, name, appearance` | Игрок вошёл в зону интереса |
| `player_leave` | `id` | Вышел или ушёл из зоны |
| `players` | `tick, list: [[id,x,y,z,ry,anim], ...]` | Позиции соседей, 15 Гц |
| `correct` | `x, y, z` | Принудительная коррекция позиции при нарушении скорости |
| `chat` | `from, text, ts` | Соседям по чанкам |
| `chunk_load` | `cx, cz, data` | `data` — бинарные байты чанка |
| `chunk_unload` | `cx, cz` | Правило порядка: `chunk_unload` отправляется раньше `chunk_load` в одном пакете |
| `cache_stats` | `loaded, max, worldTotal, bytes, bytesMax` | После каждого изменения |
| `agent_queue` | `agentId, reqId, position` | Ответ в очереди |
| `agent_token` | `agentId, reqId, token` | Поток ответа |
| `agent_done` | `agentId, reqId` | Конец ответа |
| `agent_error` | `agentId, reqId, message` | Ошибка или недоступность |
| `task_state` | `taskId, state` | Состояние задачи |
| `error` | `code, message` | Коды: `bad_msg`, `too_far`, `rate_limit`, `unauth` |

Лимиты: `pos` не чаще 30 в секунду, `chat` не чаще 5 в секунду, `npc_talk` не чаще 1 в секунду на пользователя; превышение — `error{code:'rate_limit'}` и отбрасывание.

## 5. Формат чанка (`shared/chunk-format.md`)

Файл `generated/chunks/{cx}_{cz}.bin` — один объект MessagePack:

```
{ v: 1, cx, cz, zone: 'hospital' | 'park' | 'plain',
  heights: Float32Array(17*17),             // карта высот, 16×16 ячеек
  instances: [[prefabId, x, y, z, ry, scale], ...],
  npcs: [{ id, agentId, x, y, z, ry }] }
```

`generated/world.json` — индекс: `{ v:1, chunkSize, chunksX, chunksZ, totalBytes, bytes: {"cx_cz": n}, prefabs: [{id, name, model}], districts: [{id, name, chunks: [[cx,cz],...]}], npcs: [...] }`.

Папка `generated/` в git не коммитится. Роль 1 пишет `tools/build-world`, который создаёт эти файлы. Пока он не готов, этап S1 создаёт простые фикстуры (раздел 7).

## 6. База данных (`server/db/schema.sql`)

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;

CREATE TABLE IF NOT EXISTS users (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE COLLATE NOCASE,
  pass_hash TEXT NOT NULL,
  salt TEXT NOT NULL,
  appearance TEXT NOT NULL DEFAULT '{}',
  created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS sessions (
  token_hash TEXT PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  expires_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS player_state (
  user_id INTEGER PRIMARY KEY REFERENCES users(id),
  x REAL NOT NULL, y REAL NOT NULL, z REAL NOT NULL, ry REAL NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS agent_memory (
  user_id INTEGER NOT NULL REFERENCES users(id),
  agent_id TEXT NOT NULL,
  told_cards TEXT NOT NULL DEFAULT '[]',   -- JSON-массив id карточек
  summary TEXT NOT NULL DEFAULT '',
  turns TEXT NOT NULL DEFAULT '[]',        -- последние реплики
  topics TEXT NOT NULL DEFAULT '{}',
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, agent_id)
);

CREATE TABLE IF NOT EXISTS task_progress (
  user_id INTEGER NOT NULL REFERENCES users(id),
  task_id TEXT NOT NULL,
  state TEXT NOT NULL DEFAULT '{}',
  done INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, task_id)
);
```

Модуль `server/db/index.js` экспортирует функции доступа (подготовленные запросы через `better-sqlite3`), а не сырое соединение. Файл базы: `data/city.db` (папка `data/` в `.gitignore`).

### S1. Авторизация, WebSocket, позиции (T+0:30–1:30)

Шаги:
1. `server/db/index.js` и инициализация схемы при старте.
2. HTTP API:
   - `POST /api/register {name,password}` → `{token,user}`; имя 3–20 символов, пароль минимум 4.
   - `POST /api/login` → `{token,user}`.
   - `POST /api/ws-ticket` (заголовок `Authorization: Bearer <token>`) → `{ticket, expiresIn: 30}`.
   - `GET /api/me`.
3. Пароли хешируются `crypto.scrypt` с отдельной солью, сравнение `crypto.timingSafeEqual`. Токен — 32 случайных байта (base64url), в БД хранится SHA-256 от токена, срок жизни 7 дней.
4. Тикет WebSocket — случайная строка, одноразовая, живёт 30 секунд, хранится в памяти.
5. WebSocket на `ws` в режиме `noServer: true`. Обработчик `upgrade` на `app.server` проверяет тикет в query `?ticket=` до принятия соединения. Если тикет неверный, ответить `HTTP/1.1 401 Unauthorized` и закрыть сокет. Только после успешного апгрейда принимается `hello`.
6. Один активный сокет на пользователя: новое подключение отключает старое. Проверка живости: ping каждые 10 секунд.
7. Состояние игрока в памяти; загрузка из `player_state` при входе (если нет — `SPAWN`).
8. Тик 15 Гц: для каждого игрока собрать позиции соседей из зоны 3×3 чанков и отправить `players`; события `player_join` и `player_leave` при входе и выходе из зоны.
9. Проверка скорости на сервере: расстояние между двумя `pos` не больше `MAX_SPEED · 1.5 · dt`; иначе `correct` и сброс на последнюю допустимую позицию. Ограничение координат границами мира.
10. `tools/fixtures/make-fixtures.mjs`: генерирует 144 простых чанка (плоская карта высот, несколько инстансов, зона `plain`, чанки вокруг (6,6) — `hospital`) и `generated/world.json`. Нужен, чтобы сервер и клиент не ждали `tools/build-world`.
11. Тест-клиент `scripts/ws-smoke.mjs`: регистрация, тикет, подключение, `pos`, получение `players`.
12. Тег `cp1-hello`.

Тесты:
- Пароль не хранится в открытом виде; неверный пароль отклоняется.
- Тикет работает один раз; просроченный тикет не принимается.
- WebSocket без тикета получает 401.
- Два тест-клиента видят позиции друг друга.
- Превышение скорости вызывает `correct`.

Приёмка: два браузера (или два скрипта) видят позиции друг друга; WebSocket без авторизации не подключается.

### S2. Чанки, зеркало кеша, сохранение (T+1:30–3:00)

Алгоритм потоковой подгрузки (принадлежит серверу, клиент выполняет команды):

1. Для игрока вычислить чанк `(cx, cz)`.
2. Обязательное множество $R$: все чанки с $\max(|\Delta cx|, |\Delta cz|) \le 1$ (в пределах мира).
3. Резерв: из остальных чанков взять $K = \text{CACHE\_MAX\_CHUNKS} - |R|$ ближайших по расстоянию от позиции игрока до центра чанка. Итоговое желаемое множество $D = R \cup \text{резерв}$, при этом $|D| \le 14$.
4. Зеркало кеша клиента — множество чанков, которые сервер уже отправил и не выгрузил. Разница: `toUnload = mirror \ D`, `toLoad = D \ mirror`.
5. Порядок: сначала `chunk_unload` для `toUnload`, затем `chunk_load` для `toLoad` (ближайшие первыми). После этого `cache_stats`.
6. Ограничение по байтам: сумма размеров чанков в зеркале не больше $0{,}1 \cdot B_{\text{мир}}$, где $B_{\text{мир}}$ берётся из `world.json:totalBytes`. Если ограничение по байтам нарушается, резерв сокращается (сначала самые дальние). Обязательное множество $R$ всегда загружается; если оно само не помещается по байтам, это ошибка контента и сервер пишет предупреждение в лог.
7. Инвариант: после обработки любого события $|\text{mirror}| \le 14$, а байты не превышают лимит при условии, что обязательное множество $R$ само помещается в лимит (это гарантируется контентом; тесты используют фикстуры, где это так). Проверка встроена в код: при нарушении — ошибка в логе и принудительная выгрузка резерва.
8. Пересчёт только при смене чанка игрока.

Дополнительно:
1. Сохранение состояния: `player_state` пишется раз в 5 секунд пачкой в одной транзакции для «грязных» игроков, при отключении игрока и при `SIGINT`/`SIGTERM` (корректный выход с `flushAll()`).
2. Тесты:
   - Случайное блуждание 10 000 шагов: всегда $|\text{mirror}| \le 14$ и байты не больше лимита.
   - `chunk_unload` идёт перед `chunk_load`.
   - Перезапуск сервера сохраняет позицию.
3. Тег `cp2-slice`.

Приёмка: игрок в реальном клиенте ходит по миру, на экране счётчик «X из 144», значение никогда не больше 14; после перезапуска сервера игрок возвращается на последнее место.

### S3. Мосты к агентам и задачам, боты (T+3:00–4:00)

1. Мост агента: при `npc_talk` сервер проверяет расстояние до NPC (из `world.json`) не больше `TALK_DISTANCE`, иначе `error{code:'too_far'}`. Затем вызывает `agents.reply({userId, agentId, text, context})` (контракт в `shared/agent-api.md`) и транслирует токены как `agent_token`, затем `agent_done`. Если `reply` бросает исключение или недоступен, отправить `agent_error`. Позицию в очереди (`agent_queue`) шлёт сам модуль агентов через колбэк `onQueue`.
2. Мост задач: `task_answer` передаётся в `tasks.handle(userId, taskId, payload)`; результат уходит как `task_state` и сохраняется в `task_progress`.
3. Боты (`tools/bots/index.js`): `node tools/bots/index.js --count 4 --url http://localhost:3000`. Каждый бот регистрируется (`bot1`, `bot2`, ...), получает тикет, подключается по тому же протоколу, ходит по заданному маршруту около района больницы и отправляет `pos` 10 раз в секунду. Параметр `--count 30` для нагрузочного теста.
4. Чат: `chat` рассылается игрокам в 3×3 чанках.
5. Тег `cp3-agent` ставится после того, как роли 3 и 4 подключили свои модули.

Приёмка: диалог с агентом идёт через сервер со стримингом; боты видны в мире.

### S4. Запуск, офлайн-проверка, документы, заморозка (T+4:00–5:30)

1. `scripts/start.mjs` (команда `npm start`):
   - Проверка Node.js, свободного порта 3000.
   - Проверка Ollama: `GET http://127.0.0.1:11434/api/tags`; наличие моделей `qwen3:8b` и `bge-m3`; прогрев каждой (запрос с `keep_alive: -1`). Если Ollama недоступна, сервер всё равно стартует в режиме «агенты в запасном режиме» и громко предупреждает.
   - Старт сервера.
   - Печать адресов: всегда `http://localhost:3000`; затем IPv4-адреса из `os.networkInterfaces()` (без внутренних), для каждого QR-код в терминале (`qrcode-terminal`). Если сетевых адресов нет, написать «Сеть недоступна, автономный режим».
2. `scripts/ollama-serve.sh`: запускает `ollama serve` с переменными `OLLAMA_NUM_PARALLEL=2`, `OLLAMA_KEEP_ALIVE=-1`, `OLLAMA_MAX_LOADED_MODELS=2`, `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=q8_0`. В `docs/RUN.md` предупредить: если приложение Ollama в строке меню уже запущено, его нужно закрыть, иначе переменные не применятся.
3. `scripts/check-offline.mjs` (`npm run check:offline`): ищет в `client/` и `dist/` ссылки `http://` и `https://`, кроме `localhost`, `127.0.0.1` и пространств имён (`www.w3.org`); также проверяет `<link>`, `@import` и `import ... from "https:..."`. Выводит список нарушений и завершается с ошибкой.
4. Эндпоинт `/admin/stats` только для `127.0.0.1`: онлайн-игроки, размер кеша каждого игрока, память процесса, состояние Ollama. Простая HTML-страница `/admin`.
5. Документы:
   - `docs/RUN.md`: запуск с нуля (`npm ci`, модели, Ollama, `npm start`), оба режима.
   - `docs/OFFLINE_TEST.md`: пошаговая проверка с выключенным Wi-Fi (раздел 9).
   - `docs/DEMO_RUNBOOK.md`: сценарий вечера: порядок действий, что говорить, что делать при сбоях.
6. Автопереподключение: сервер должен корректно принимать повторное подключение того же пользователя с новым тикетом без потери состояния.
7. Заморозка: с T+5:00 новых функций нет. Теги `draft-v0` и затем `demo-ready`.

Приёмка: `npm start` без интернета проходит; `check:offline` зелёный; два окна браузера (одно в режиме инкогнито) входят разными пользователями на `localhost` при выключенном Wi-Fi.

## 8. Автотесты роли 2 (сводка)

| Область | Проверка |
|---|---|
| Протокол | encode/decode туда и обратно; невалидные сообщения отклоняются |
| Авторизация | хеш, неверный пароль, срок токена |
| WebSocket | 401 без тикета, одноразовость тикета, один сокет на пользователя |
| Позиции | коррекция при превышении скорости, границы мира |
| Кеш | инвариант $\lvert\text{mirror}\rvert \le 14$ и по байтам на 10 000 шагах блуждания; порядок unload → load |
| Сохранение | запись и чтение `player_state`, `flushAll()` при выходе |
| Мосты | `too_far`, потоковая доставка токенов, `agent_error` |
| Офлайн | `check:offline` падает на тестовой внешней ссылке |

## 9. Ручные проверки тимлида (человек)

| Точка | Что делаешь сам |
|---|---|
| T+0:30 | Клонируешь на втором ноутбуке, `npm run setup`, `npm start`, открываешь `/health` |
| T+1:30 | Два браузера (разные профили) видят друг друга; WebSocket без логина не подключается |
| T+3:00 | Идёшь по миру, смотришь счётчик кеша, перезапускаешь сервер и проверяешь, что позиция сохранилась |
| T+4:30 | Живой диалог через сервер, боты ходят |
| T+5:00 | Тест «Wi-Fi выключен»: (1) сервер запущен при Wi-Fi, подключить второй ноутбук (режим A); (2) выключить Wi-Fi на сервере; (3) открыть `http://localhost:3000` в новом окне (инкогнито для второго игрока); (4) оба игрока видят друг друга и ботов; (5) диалог с агентом работает; (6) перезапустить сервер, состояние на месте |

Важно: в режиме B игровой клиент хоста должен быть открыт через `localhost`, а не через LAN-адрес. Если страница была открыта по LAN-адресу, её нужно перезагрузить по `localhost`.

## 10. Взаимодействие с другими ролями

- Контракты `shared/*` меняет только эта роль. Запросы от других ролей приходят в чат или в `docs/CONTRACT_CHANGES.md`.
- Заглушки в чужих папках принадлежат владельцам и заменяются ими без согласования, пока сохраняется экспортируемый интерфейс.
- Интеграционные слияния: каждые 45–60 минут `git fetch && git rebase origin/main`, `npm run verify`, пуш.
- Если `main` сломан, откат отдельным коммитом `git revert` и сообщение в чат.

## 11. Когда Claude Code должен остановиться и спросить человека

1. Нужно изменить контракт (`protocol.js`, формат чанка, схему БД, интерфейс агента).
2. Нужна зависимость вне списка.
3. Тест падает два раза подряд по неочевидной причине.
4. Для задачи требуется правка в чужой папке.
5. Действие необратимо: удаление данных, переписывание истории git, сброс базы.
6. Возникло расхождение со спецификацией или двусмысленность, влияющая на другие роли.
